# Flame and Blame — "Blame Chain" demo

Contest demo for RetroStyle Games' Flame and Blame Dev Contest (deadline 27 Nov, 23:59 Kyiv).
A first-person firefighter physics comedy. One scene: an apartment (kitchen + living room) is on fire.
The player fights the fire with a physics hose. Every event remembers WHO caused it, and the game
shows the chain of blame live (Blame Feed) and at the end (Damage Bill + Verdict).

The judges score: Taste (funny, readable at a glance), Complexity (physics, particles, camera react to
every action), Interaction (systems affect each other), Stability (no crashes or freezes in WebGL),
Presentation. They watch a video and play the build. Code may be reviewed for finalists, so the code must
show senior-level architecture.

## Tech stack (fixed, do not change without asking)
- Unity 6 (6000.x LTS), URP, target platform **WebGL** (Windows exe as fallback)
- Extenject/Zenject (DI, SignalBus, MemoryPool, PlaceholderFactory) via OpenUPM
- UniTask (Cysharp) via OpenUPM — no coroutines in gameplay code
- New Input System — actions are defined **in code** (InputService), no .inputactions assets
- ScriptableObject configs for every tunable number and every interaction rule
- Exception (decided by the user): a few complex silhouettes use **CC0 models from Kenney Furniture Kit**
  (`Assets/_Project/Models/Kenney`, license included), recolored into the palette via `PropModels` / `LevelLayoutConfig`.
  Do not add other third-party assets without asking.
- No paid assets. All other visuals are **procedural**: primitives, generated meshes, palette materials,
  textures generated by code, Shuriken particles. (VFX Graph is NOT supported on WebGL — never use it.)

## Architecture rules
- Folders: `Assets/_Project/{Scripts,Configs,Prefabs,Materials,Textures,Scenes}`, editor code in `Assets/_Project/Editor`.
- Assemblies (asmdef): `FB.Core`, `FB.Game` (gameplay + blame + UI in namespaces), `FB.Editor`.
  Dependency direction: Game → Core. Core depends on nothing project-specific.

## TIME BUDGET: the whole project is built in 2 days
- Scope is cut on purpose. Do not add features, abstractions or polish that the current session prompt does not ask for.
- Prefer the simplest implementation that is still clean (DI, signals, pools, MVP) and visibly works in a video.
- Stability over features: if something is risky, propose a simpler variant first.
- Composition root: `ProjectInstaller` (ProjectContext) + `GameplayInstaller` (SceneContext). All wiring in installers.
- **No singletons, no `FindObjectOfType`, no `GameObject.Find`, no static mutable state.**
- Communication between systems: Zenject **SignalBus** (Observer). Signals are immutable structs/classes in `Signals/`.
- UI = **MVP**: passive `View` (MonoBehaviour, no logic) ↔ `Presenter` (plain C#, injected, IInitializable/IDisposable) ↔ `Model`/service.
- Spawned objects (droplets, fire particles, puddle cells visuals, feed entries, popups, decals) go through
  **pools** (Zenject MemoryPool or a generic `IPool<T>`). Zero `Instantiate`/`Destroy` during gameplay.
- Simulation systems are plain C# classes implementing `ITickable`/`IFixedTickable`, ticking all entities
  centrally (e.g. fire at 10 Hz) instead of `Update()` on every MonoBehaviour.
- Patterns we want visible: DI, Observer (signals), MVP, Object Pool, Factory, State Machine (game flow, civilian AI),
  Strategy (interaction rules), Facade (`IHoseFacade` etc.), data-driven configs.
- Interfaces over concrete types at system boundaries (`IFlammable`, `IWettable`, `IConductive`, `IBlameService`, ...).
- Every gameplay effect carries a `Cause` (see Blame module). Never apply damage/status without a Cause.

## Code style
- C# 9, `sealed` by default, `readonly` where possible, explicit access modifiers.
- English names and comments. XML doc only on public interfaces.
- No allocations in hot paths (use NonAlloc physics queries, pooled lists, struct signals where sensible).
- `[SerializeField] private` instead of public fields. Configs: `[CreateAssetMenu(menuName = "FB/...")]`.

## Scene and asset creation (important for working without the Editor UI)
- Do NOT hand-edit .unity / .prefab YAML. Build scenes and prefabs with **Editor scripts**
  (menu `Tools/Flame&Blame/...`) using `PrefabUtility.SaveAsPrefabAsset`, `EditorSceneManager`, `AssetDatabase`.
- The level is described by a `LevelLayoutConfig` ScriptableObject (rooms, walls, doors, props) and generated by
  `Tools/Flame&Blame/Rebuild Level`. Rebuilding must be idempotent.
- Colors come from one `PaletteConfig` SO. Style: bright, cartoony, flat-shaded low-poly, readable silhouettes.

## WebGL constraints
- No threads, no `System.Threading.Tasks.Task.Run`; UniTask on PlayerLoop only.
- IL2CPP stripping: keep `link.xml` preserving Zenject and FB.* assemblies; Managed Stripping Level = Minimal.
- Keep draw calls low (shared materials, GPU instancing on), particle counts capped in configs.
- Build settings: Compression Gzip with Decompression Fallback (for itch.io / GitHub Pages hosting).

## How to work in this repo
- Work **module by module**. A module is done when: it compiles with no warnings from our code, the user can test it
  in Play Mode with steps you list, and docs are updated.
- At the end of each module:
  1. List exact manual steps in Unity Editor (menus to click, what to look at), keep them minimal.
  2. Append 3–5 lines to `Docs/AI_LOG.md`: what was generated, key decisions.
  3. Briefly explain the 2–3 most important design decisions so the user can defend them in the video and interview.
  (`Docs/ARCHITECTURE.md` is written once, in the last session.)
- If something is ambiguous, ask before writing large amounts of code.
- Prefer small, reviewable files (< 200 lines). One class per file.
